# Work 模式产品需求与设计规范

> **版本**：v1.0（需求基线）  
> **日期**：2026-10-18  
> **适用范围**：Windows 桌面 AI Agent 的 Work 模式第一版  
> **文档用途**：作为 AI Coding 工具实施、代码审查及验收的统一依据。  
> **状态说明**：标记为【已确定】的内容来自需求讨论；标记为【实现约束】的内容是为满足既定需求而必须遵守的逻辑边界；标记为【待定】的内容不可由 AI Coding 工具自行当成已决策方案。

## 0. 阅读与实施规则

1. **需求优先级**：本文“已确定需求”高于示意结构、伪代码、示例命名和“建议实现”。现有 Chat 功能不可因 Work 开发而退化。
2. **不擅自扩展**：不要自行加入多 Agent、强制计划模块、复杂任务调度平台、GUI 自动化、用户 Skill 商店、长期记忆系统等。
3. **区分产品需求与技术方案**：Windows 沙箱的具体技术、外部授权实现方式、IPC 和持久化格式尚未选定；需要结合现有项目代码评估后确定，不得直接假设。
4. **以现有实现为基础**：先检查已有模型调用、聊天、联网搜索、历史记录和 UI 代码，尽量复用；不要另建重复的 API 客户端或聊天体系。
5. **涉及安全时不得降级实现**：若某项隔离无法可靠实现，应明确列为阻塞项，不得以字符串路径判断、隐藏目录或普通进程启动冒充 OS 级沙箱。

## 1. 产品目标与范围

### 1.1 产品定位【已确定】

桌面软件分为 **Chat** 和 **Work** 两种模式：

- **Chat**：已完成。仅提供基础模型对话、回复生成和联网搜索，不获得本地文件或命令执行能力。
- **Work**：待开发。轻量级、以文件为中心的本地办公 Agent。用户以自然语言提出任务；Agent 自主决定步骤、工具和 Skill，在受控环境中处理文件、执行命令并交付成果。

Work 的目标是“用户说出需求，Agent 尽可能自主完成工作”，而不是完整复制大型专业工作 Agent。

### 1.2 第一版能力边界【已确定】

支持：文件阅读与生成、文档/演示文稿/表格等办公任务、命令及脚本执行、联网搜索、联网下载、按需安装当前对话额外依赖、按需申请沙箱外权限、任务中途自然语言干预、并发工具执行、多对话同时运行、文件交付胶囊。

不支持：控制其他软件的鼠标键盘、跨应用 GUI 自动化、强制每个任务创建计划、多 Agent 体系、任务快照回放、第一版自动上下文压缩、用户安装/管理 Skill、关闭窗口后的系统权限审批通知。

## 2. 高层架构

### 2.1 逻辑组成【已确定／实现约束】

```text
Windows 桌面应用
├─ 展示层（窗口，可关闭并重新打开）
│  ├─ Chat UI（现有）
│  └─ Work UI：对话、状态、审核、执行详情、交付胶囊
├─ 应用后台核心（不依赖窗口生命周期）
│  ├─ 模型通信层（复用现有 OpenAI 兼容协议）
│  ├─ Work Agent Loop（按对话管理）
│  ├─ 工具调度与结果关联
│  ├─ 权限审核与授权状态管理
│  ├─ 工作区与历史记录管理
│  └─ Skill 发现与加载
└─ 受限执行环境（按需启动执行进程）
   ├─ 基础文件工具
   ├─ 命令／脚本执行与子进程
   └─ 网络访问及对话级依赖安装
```

**关键边界**：模型提出动作，应用验证/调度，低权限执行环境执行；权限审批由可信应用组件控制。不能让模型直接改变权限策略。

### 2.2 单 Agent、多实例【已确定】

每个正在运行的 Work 对话使用一个主 Agent Loop；不采用多角色、多模型代理协作结构。不同对话可以各自运行自己的 Agent Loop，并行工作。“单 Agent”不代表全应用只能运行一个任务。

## 3. Agent 的基本执行机制

### 3.1 Agent Loop【已确定】

1. 收到用户消息，并读取当前对话历史与可用工具、Skill 概览。
2. 使用现有 OpenAI 兼容云端 API 请求模型（采用**原生 Tool Calling**）。
3. 模型可直接回复，也可返回一个或多个工具调用。
4. 执行器校验调用、处理必要的审核并执行工具，把真实结果按 `tool_call_id` 关联返回模型。
5. 模型根据反馈自行决定继续、重试、调整策略、询问用户或结束。
6. 结束时提供用户可读的总结；需要交付的文件可附交付胶囊。

不要求每一步生成计划；允许模型自行在适当场景规划。禁止把普通文本或模型输出的任意 JSON 当作 Tool Calling 的替代机制。

### 3.2 多工具并行【已确定】

- 同一轮模型响应中的多个工具调用允许并发执行，而非强制串行。
- 每项调用独立跟踪状态、参数、结果和错误；结果必须准确绑定各自的 `tool_call_id`。
- 一批调用完成（含成功、失败、拒绝或取消的结果）后，再将该批结果整体提供给模型，进入下一轮决策。
- 一个调用失败不自动取消其他调用；交由模型判断。
- 对明确冲突的资源操作，执行器可实施必要的冲突控制，不能以“并行”为由破坏文件一致性。
- 并行调用仍须逐项进行权限检查；等待审批的调用不得先执行。其他独立调用可以完成，但该轮模型决策必须遵守批次结果完整性。

**实现约束**：并发上限、冲突检测粒度和调度算法待开发阶段确定；不得改变“可并发且结果不串线”的产品行为。

### 3.3 任务中途插入消息【已确定】

- Work 执行期间仍允许用户向**同一对话**发送新消息。
- 新消息立即纳入持久化对话历史并在 UI 展示。
- **不因普通新消息强制中断正在运行的工具**。
- 当前工具调用批次结束后，将此前积累的新消息**一起**纳入下一次模型请求，模型综合最新要求自行调整行动。
- 消息顺序须保留；“合并处理”指同轮交给模型，不是覆盖、去重或擅自改写用户原话。

示例：用户依次说“改成深色”“加一页介绍”“还是浅色”。下一轮模型应能看到三条按时间排列的消息，并以最后的风格要求为准，同时考虑新增页面要求。

### 3.4 Chat 发起 Work 请求【已确定】

- Chat 模型只额外获得一个受限的 `request_work` 工具，用于提议把需要本地文件、命令、多步骤办公处理或成果交付的任务交给 Work；不得向 Chat 暴露任何 Work 本地工具。
- `request_work` 只生成标题、执行提示词和必要的上下文摘要，并持久化为待批准请求。模型调用本身不得创建对话、工作区或开始执行。
- 桌面 Chat 必须展示请求卡片。只有用户明确批准后，可信应用后端才创建独立 Work 对话和工作区并在后台开始任务；拒绝时不创建任何 Work 资源。
- 批准后默认停留在当前 Chat，不强制切换页面；卡片提供打开目标 Work 的入口。目标 Work 提供返回来源 Chat 的入口。
- Work 接收经用户批准并在卡片中展示的执行提示词，以及明确标记为“由 Chat 模型整理、可能不完整”的背景摘要；不默认复制完整 Chat 历史，摘要不构成权限授权。
- 请求、批准结果、来源关系和目标关系需要持久化。重复批准必须幂等，不能创建多个目标 Work 对话。
- AI 卡片可以触发 Chat 消息和提议，但批准动作只允许在桌面端完成。

## 4. 对话工作区与文件

### 4.1 工作区结构【已确定】

每个 Work 对话有独立且持久化的工作区，包含三个默认子目录：

```text
Workspaces/
└─ <conversation-id>/
   ├─ inputs/    # 用户上传的原始文件
   ├─ work/      # 脚本、素材、中间产物等
   └─ outputs/   # 面向用户的产出成果
```

- **整个工作区由 Agent 自主管理**；三个子目录只是用途约定，不是三套相互隔离的权限域。
- 工作区在对话切换、窗口关闭、软件正常退出或重新打开后仍然存在。
- `inputs/`：聊天上传的文件由软件复制进入，保留外部原文件；同名冲突需要安全处理，具体命名规则待定。
- `work/`：Agent 自行管理工作过程。
- `outputs/`：放置最终或准备交付的成果文件。
- 用户无需通过文件管理器直接维护内部工作区。

### 4.2 本地外部文件【已确定】

用户可以直接在自然语言里指定本地文件或目录（例如 `D:\学习资料`）。这**不是独立的“本地路径引用功能模式”**，而是通用 Agent 按需申请沙箱外权限并完成任务的正常表现。未经批准，Agent 不可擅自读取或修改工作区外资源。

### 4.3 文件交付胶囊【已确定】

- Agent 可以自主决定在适当时间生成文件交付胶囊，通常对应 `outputs/` 中的文件，也允许阶段性成果交付。
- 胶囊是**文件引用**，不复制文件，也不触发浏览器下载。
- 在 Windows 桌面端点击胶囊，使用**文件资源管理器定位并选中对应文件**。
- 系统须在展示/触发时检查文件是否存在，丢失时明确提示，不得出现无效的静默点击。
- 交付接口只负责展示或登记成果，不隐式搬运文件；文件在工作区内的移动由 Agent 负责。

## 5. 工具体系

### 5.1 第一版基础工具【已确定】

| 工具（建议命名） | 主要用途 | 边界 |
| --- | --- | --- |
| `execute_command` | 执行命令、脚本及必要子进程 | 必须经过 OS 沙箱约束，不能逃逸 |
| `read_file` | 读取文件 | 按有效文件权限访问 |
| `write_file` | 创建、修改文本文件 | 按有效文件权限访问 |
| `list_directory` | 枚举目录及文件 | 按有效文件权限访问 |
| `web_search` | 检索公开网络信息 | 复用现有搜索能力 |
| `deliver_files` | 生成文件交付胶囊 | 只能引用有效成果文件 |

名称、参数类型与工具响应结构可以根据现有代码统一，但**能力语义不可被缩减**。复杂办公任务优先通过命令执行、脚本和 Skill 完成，不强制为 Word/PPT/Excel/PDF 各自新增底层工具。

### 5.2 Skill 体系【已确定】

- 采用行业常见的**技能目录 + `SKILL.md`** 格式，允许可选的 `scripts/` 与辅助资源。
- 采用**渐进式加载**：先向模型提供技能名称、说明等摘要信息，再由 Agent 决定是否读取对应 `SKILL.md` 和资源。
- 第一版只发行**内置 Skill**；不做用户自主安装、删除和管理的 UI／功能。
- Agent 在任务中**可以主动申请沙箱外授权**，批准后可创建或修改软件的 Skill 目录内容；但这并非默认的 Skill 自修改流程，也不代表 Agent 默认有权限修改内置 Skill。
- Skill 指令不拥有系统安全策略上的优先权：不能绕过沙箱、审批或用户要求。

### 5.3 Skill 与运行依赖【已确定】

软件提供所有 Work 对话共享的基础运行环境（计划预置 Python 及常用办公依赖）；额外依赖可按需安装在**当前对话自己的工作区范围内**，不能污染共享基础环境。具体依赖列表、安装布局、打包方式由实现阶段决定。不得通过用户机器上恰好安装的软件来冒充“开箱即用”。

## 6. 安全隔离与授权

### 6.1 默认隔离【已确定】

- 本地文件和命令执行应集中在低权限、独立的受限执行进程中；由操作系统的权限机制实现真正的隔离。
- 默认只授权当前对话工作区及运行环境必需的受控资源，不允许读写其他用户文档或其他对话工作区。
- **命令执行以及它启动的子进程**必须继续受同等约束，不能通过 PowerShell、Python、子进程、符号链接／目录联接等方式绕过限制。
- 基础工具和命令工具服从同一个安全策略。
- 共享基础运行环境原则上提供必要的可执行/读取访问，而不是给执行进程开放对共享环境的随意修改权限。

**技术事实提醒**：仅使用低权限令牌、检查输入路径前缀或指定工作目录，并不能单独保证“只能访问工作区”；具体 Windows 令牌、ACL、容器机制仍需安全设计与验证。

### 6.2 沙箱外授权【已确定】

Agent 可以为具体任务请求沙箱外操作，必须由用户批准。支持：

1. **单次操作授权**：仅授权所批准的指定操作。
2. **当前任务期间的目录授权**：指定目录、指定能力（如只读／读写），任务结束后失效。

原则：默认拒绝、最小权限、不得静默扩权；目录文件访问授权**不自动等同于**任意外部命令执行授权。授权有效性由可信程序持有和检查，不由模型对话文本、Skill 内容或摘要自行定义。

### 6.3 审核等待【已确定】

- Agent 请求审核后，需授权的操作进入等待状态，未经批准不可执行。
- 用户**批准**后，Agent 自动继续；用户**拒绝**后，结果反馈模型，由模型决定替代步骤。
- 不设短时倒计时自动批准或拒绝；用户未处理则持续等待。
- 第一版窗口关闭时**不发送系统审批通知**。后台任务可处于等待状态，窗口重新打开后仍可审批。
- 后续版本可以增加系统通知，点击后返回相关对话审批界面。

### 6.4 网络权限与风险【已确定】

- `web_search` 可用，沙箱进程及其子进程也**允许直接联网**，普通请求不逐次审批。
- 因而支持联网下载、访问 API、安装额外依赖。
- **明确风险**：有网络权限的程序可以向外发送其可读取的数据。OS 文件沙箱不能单独防止工作区内容外传；不要在文档或 UI 中宣传其具备未实现的网络防泄漏能力。

### 6.5 沙箱技术待定【待定】

以下必须通过后续技术调研及现有代码评估确定：

- Windows 权限隔离方案：受限令牌／ACL、AppContainer 或其他可行机制。
- 沙箱外批准后是由可信代理执行明确操作，还是在安全边界内动态扩展资源访问。
- IPC 机制、Worker 生命周期、权限回收、资源隔离、系统兼容性及安全测试方案。

**强制要求**：技术选择不能改变本章产品安全语义；若不能达成，应显式报告差距并阻止按“已完成沙箱”验收。

## 7. 任务状态、停止与恢复

### 7.1 主动停止【已确定】

- 用户点击“停止”后，立刻阻止发起新一轮模型请求及新工具调用。
- 尽快取消当前模型请求，终止正在运行的工具与其子进程，包括并行批次中的所有操作。
- 文件操作尽可能取消，但**不承诺回滚**；已写入工作区的文件予以保留。
- 保留聊天历史、工具记录，UI 显示“已停止”而不是继续转圈。
- 等待权限审核时也可停止；被停止的任务不得因迟到的审批结果而继续执行。

### 7.2 自然语言继续【已确定】

停止后返回普通聊天状态，用户可发送“继续”“重新生成”等消息。没有专门的恢复按钮、快照或步骤回放系统；Agent 根据历史和现有文件检查状态并自行继续。对未完成或被强行终止的操作，不可凭历史假定成功。

### 7.3 错误恢复【已确定】

- 工具失败时返回真实错误，模型自主决定重试、变更方案、求助或结束。
- 不设置业务层面的固定重试次数或“连续错误自动放弃”策略。
- 仍受用户停止、OS 资源约束和安全权限策略约束；不能借“修复失败”绕过审核。

## 8. 多对话并发与应用生命周期

### 8.1 不同对话同时运行【已确定】

- 不同 Work 对话的 Agent Loop 可以同时执行；切换对话不会暂停旧任务。
- 各自保持独立的历史、工作区、执行状态和授权状态。
- 某个对话在等待审核时，不阻塞其他对话。
- 每个对话不必始终占用固定的执行进程；进程创建与复用策略待定，但不能破坏隔离。

### 8.2 窗口与后台【已确定】

- **关闭或最小化窗口**：仅改变显示层，后台 Agent 继续工作。
- **重新打开窗口**：从后台运行状态同步当前任务，呈现实时进度、历史及待处理审核。
- **真正退出整个软件**：尽快停止全部 Agent Loop、工具和子进程；保留持久化历史与工作区。
- **异常崩溃**：尽可能保证受限子进程不会无限孤儿化；已持久化数据保留。具体看门狗/进程组方式待定。

## 9. UI 与用户体验

### 9.1 执行过程展示【已确定】

- 默认显示**简洁的执行进度/当前状态**，允许展开查看工具调用详情。
- 详情至少包含工具名、参数（敏感内容做适当掩码）、执行结果／错误及耗时。
- 依据真实执行事件自动更新状态；没有可信进度百分比时不伪造数字。
- Agent 可主动发简短说明，但不强制每次调用都生成文字。
- 完成或停止后仍可查看执行历史；工具事件不应默认变成大量独立聊天气泡。
- 文件成果以交付胶囊展示；点击由资源管理器定位文件。

### 9.2 审批体验【已确定／实现约束】

审核请求应向用户说明：Agent 希望执行什么、影响哪些具体文件/目录、申请何种能力、授权有效范围。用户可以批准或拒绝；拒绝不会被程序自动当成批准。窗口关闭期间保留审核请求，第一版不额外弹系统通知。

### 9.3 用户体验原则【已确定】

Work 是自然语言任务界面，而非 IDE 或工作区文件管理器。用户不需要手动制定工具步骤、手动拷贝上传文件进目录、手动移动输出文件，也不需要理解沙箱技术才能使用。

## 10. 模型上下文与历史

### 10.1 第一版【已确定】

- 现有 Chat／Work **复用相同模型通信基础设施**，通过 OpenAI 兼容云端 API 调用模型，使用原生 Tool Calling。
- 聊天历史和工具执行历史持久化保存；工作区与历史分别管理。
- 本条已由 2026-10-21 的《上下文管理系统需求规范》取代：Chat 与 Work 均实现自动上下文压缩，完整原始历史继续独立保存，不能静默删除或改写。
- 上下文构造与原始完整历史的数据模型分离，为未来压缩留接口。

### 10.2 后续版本【已确定方向】

未来引入**自动上下文压缩**：保留完整原始记录，生成面向模型的压缩上下文，保留关键用户要求、任务进展和文件位置。权限授权状态始终由独立可信模块维护，不能被摘要代替。长期记忆/向量库未纳入当前计划。

## 11. 关键运行流程（验收参考）

### 11.1 普通办公任务

1. 用户上传文件；软件复制至当前对话的 `inputs/`。
2. 用户说“根据资料制作 PPT”。Agent 选择适当 Skill（如有），调用工具读文件、制作内容。
3. 需要脚本时在受限环境执行；临时成果存入 `work/`，最终成果放入 `outputs/`。
4. Agent 检查生成结果并回复，主动发出 `deliver_files` 胶囊。
5. 用户点击胶囊，Windows 文件资源管理器定位并选中 `outputs/` 对应文件。

### 11.2 外部目录任务

1. 用户说“整理 `D:\学习资料`”。
2. Agent 自行发现当前操作需要沙箱外访问，申请明确的文件/目录权限。
3. 未批准前不执行越权操作；批准后按授权范围继续；拒绝则返回模型判断替代方案。
4. 授权只对本次具体操作或当前任务期间指定目录有效，不跨任务自动保留。

### 11.3 执行中补充要求

1. Agent 正并发执行若干工具；用户连续发送三条调整要求。
2. UI 立即展示并持久化消息，工具继续完成当前批次。
3. 批次结束，全部新增消息按原顺序进入下一轮模型上下文。
4. 模型综合最新要求调整后续工作，而不是每来一条就取消工具。

### 11.4 关闭窗口与退出软件

1. 用户关闭窗口，对话 A 和 B 仍在后台执行。
2. A 遇到需要审核的操作，保持等待；B 可继续运行。
3. 用户重新打开窗口，可查看最新执行状态与 A 的审核请求。
4. 用户选择“退出软件”，全部任务及子进程尽快停止，历史与工作区保留。

以下用例属于**可验证的完成标准**；通过模拟模型响应、模拟工具、真实工作区与沙箱测试联合验证。

## 13. 明确不在第一版范围内

- 多 Agent 协作、强制计划器、复杂任务队列/计划回放系统。
- 浏览器或其他桌面应用的 GUI 控制与跨应用自动化。
- 用户安装、导入、删除、启停或管理 Skill 的产品界面。
- 默认由 Agent 自主修改 Skill 的独立功能（经沙箱外批准的普通文件修改不受此条否定）。
- 自动上下文压缩、长期记忆、向量检索。
- 后台权限审批 Windows 系统通知或直接在系统通知上授予权限。
- 文件下载式交付、强制用户管理内部工作区的文件管理器。
- 每次工具调用强制显示独立聊天气泡、伪造任务进度百分比。

## 14. 未确定项目与开发阶段决策清单

以下**不是未解决的产品愿景问题**，而是需要检查现有代码和 Windows 支持条件后才能敲定的技术方案：

1. **Windows OS 沙箱**：具体令牌/容器/ACL 实现、跨对话隔离、子进程继承、文件链接与系统资源访问的防绕过测试。
2. **沙箱外操作执行通道**：可信代理代理执行，还是动态授予沙箱访问；如何审查、撤销权限和保障目录授权范围。
3. **Worker 与 IPC**：进程创建、健康检查、异常回收、通信协议和线程调度。
4. **并发**：最大并发量、资源冲突控制、批次调度和取消机制。
5. **历史与任务状态数据结构**：持久化格式、日志裁剪与文件安全策略（不得删除用户原始历史）。
6. **基础运行环境**：Python/办公库具体版本、打包方式、对话额外依赖安装目录。
7. **内置 Skill 清单**：优先覆盖 PDF、Word、PPT、表格等，但正式列表、脚本依赖与质量标准待选。
8. **文件安全细节**：上传文件重名、输出文件删除/移动后的胶囊失效、特殊路径处理。
9. **UI 具体样式**：按当前产品设计语言实现，本文仅固定行为与信息要素。
10. **系统资源约束**：命令进程资源限制、超时与清理策略；不得转化为业务层面“模型重试 N 次就停止”。

## 15. 面向 AI Coding 工具的实施边界

### 15.1 建议的实施顺序（非已选具体技术）

1. **代码审计**：先标注可复用的 Chat API、原生 Tool Calling、消息持久化和搜索代码，确认窗口与后台运行关系。
2. **领域模型**：搭建 Work 对话工作区、执行状态、工具事件、审批请求和交付引用的持久化模型。
3. **执行骨架**：在模拟工具下跑通 Agent Loop、并行结果关联、插入消息批次和停止逻辑。
4. **安全阻塞项**：在接入真实 `execute_command` 之前完成 Windows 沙箱选型与越权测试，绝不可先交付不受控执行器作为“最终版”。
5. **工具、Skill 和运行环境**：按边界接入基础工具、内置 Skill、共享基础环境及对话额外依赖。
6. **UI 与生命周期**：接入简洁进度、详情、审批、交付胶囊、后台运行/重新开窗同步。
7. **端到端验收**：逐项跑第 12 章；分别测试用户停止、拒绝授权、异常崩溃和多对话并行场景。

### 15.2 AI Coding 工具的禁止行为

- 未检查现有代码就推倒重写 Chat 或模型 API 模块。
- 用提示词“请只访问工作区”代替操作系统隔离。
- 通过仅比对字符串前缀阻止文件越权，或忽略子进程、符号链接等绕过路径。
- 自动同意权限申请、赋予 Worker 管理员权限、在拒绝后换个工具悄悄重试同一越权操作。
- 以“支持并发”为由丢失、错配工具结果，或普通插话直接杀掉当前命令。
- 将工作区文件展示/交付设计成下载 API，或者把用户导入的原文件当作可随意覆盖的外部文件。
- 将【待定】方案直接改写为“已确定”，或添加超出范围的大型系统。
