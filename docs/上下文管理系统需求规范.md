# Chat / Work 上下文管理系统需求规范

> 版本：v1.0 · 日期：2026-10-21 · 类型：产品需求与行为规范 · 状态：需求基线
>
> 适用范围：Windows 桌面 AI 助手的 Chat 与 Work 模式。本文描述“系统应实现什么”，不绑定现有代码目录、类名、UI 框架或模型供应商。

## 1. 背景与目标

现有 Chat 长对话会逐渐遗漏较早的讨论内容；Work 在长期运行及大量工具交互后容易触及上下文限制，可能需要用户新建对话。这两种问题都不应以“清空或放弃当前会话”作为常规解决方式。

**总体目标：** 构建一个对用户尽量无感的统一上下文管理系统，持续对完整模型请求进行 Token 预算检查，在安全时机自动压缩可压缩历史，并保留可靠的原始历史回溯能力，使 Chat 能延续长期讨论、Work 能连续执行较长任务。

**成功标准：** 在模型服务可用且最小必要请求可以容纳的前提下，普通的上下文增长不得直接导致强制新建对话；所有历史消息仍可从应用记录中恢复；压缩不得破坏工具调用状态、授权边界或正在执行的任务。

## 2. 范围、优先级与约束

### 2.1 本期必须交付（P0）

- 完整请求级 Token 预算：覆盖提示词、工具 Schema、已注入 Skill、历史、工具消息、当轮输入、多模态估算及输出预留。
- Chat / Work 共用上下文底座，采用不同压缩重点与历史访问入口。
- 压缩前的历史持久化、滚动状态摘要、近期原文保留及自动触发。
- Work 历史工作区副本和现有 CLI 检索入口；Chat 专用历史查询工具。
- 关键词 + 本地向量混合检索、可回退的索引、基本权限与隐私防护。
- Tool Calling 安全边界、异常恢复与连续运行的验收测试。

### 2.2 可分阶段优化（P1）

- 更好的相似消息去重、查询重写、检索结果重排、自动参数调优。
- 可选的外部 Embedding 服务、细粒度诊断面板与多种摘要质量评估。
- 对超大规模历史采用更高效的向量索引结构。

### 2.3 非目标

- 不要求复刻 ChatGPT 内部的非公开上下文管理实现，也不依赖特定供应商的 Compaction API。
- 不要求 Work 增加专用“历史搜索”模型工具；不新增为了读取应用内部目录的沙箱权限。
- 不让摘要替代权威原始历史；不把模型产出的摘要视为可信执行状态或权限凭证。
- 不承诺模型 API 完全不可用、服务商能力不匹配、单条不可拆输入超出上下文时仍可无条件执行。

## 3. 总体架构与运行原则

**统一组件职责（逻辑模块，不要求拆成独立进程）：**

| 逻辑职责 | 应提供的能力 |
| --- | --- |
| Context Manager | 管理每个会话的摘要版本、压缩边界、并发和状态协调 |
| Token Budget | 组装完成后计算整体请求开销、输出保留与安全余量 |
| Context Compactor | 独立压缩请求、分批压缩、摘要校验、原子切换及回退 |
| History Store | 保存权威消息事件、完整工具关联、版本及原始附件引用 |
| History Search | 全文索引、Embedding 索引、混合排序和消息定位 |
| Work Exporter | 将可导出的历史副本、搜索脚本与索引放进当前工作区 |

**运行原则：** “权威历史永久独立保存 → 按预算构建当前模型上下文 → 达阈值时压缩旧上下文 → 保留近期完整消息 → 必要时回查原始历史”。Chat 和 Work 使用相同的基础机制，但 Work 的回溯通过既有文件/命令能力完成，Chat 通过单一 Tool Calling 工具完成。

## 4. 完整模型请求的 Token 预算（REQ-TKN）

- **REQ-TKN-01** 系统必须在每一次模型请求发送前，基于当次**实际待发送载荷**估算或计量 Token，而非只统计聊天消息文本、消息数量或历史总长度。
- **REQ-TKN-02** 计入项至少涵盖：System / Developer / 模式提示词、工具名称与 JSON Schema、实际注入的 Skill 内容、摘要、近期及未压缩历史、工具调用参数和结果、当轮用户消息、附件转写/提取内容、供应商特有消息封装开销。
- **REQ-TKN-03** 图片、音频及其他非纯文本内容应依据模型提供的计数接口或模型适配器作预算；如无法准确计算，必须标注为估算，并增加保守余量，不能按零 Token 处理。
- **REQ-TKN-04** 系统按本次模型能力与配置确定上下文上限 C、输出预留 O、安全余量 S，输入预算 B = C − O − S。只有待发送输入不超过 B 时才允许发起正常请求。
- **REQ-TKN-05** 优先使用供应商提供的计数能力或相应模型 Tokenizer；缺少时使用可校准的保守估算。响应返回后记录可获得的实际 Usage，以校准预估误差。
- **REQ-TKN-06** 模型切换、工具集合变化、Skill 加载变化、输出上限变化及新增附件时，都必须重新计算预算；不允许沿用过时的 Token 结果。
- **REQ-TKN-07** 最小必要提示词、待处理新用户输入和最小输出空间不应通过“删除历史”之外的虚假手段压低统计；若仍无法容纳，进入有说明的受限状态，而非悄悄截断用户输入。

**建议默认值（可配置）：** 预算使用率 70% 为软阈值，80% 为优先压缩阈值；压缩目标约为 50%–60%。安全余量、输出预留和阈值必须可按模型调整。这些是初始参数，并非不可变常量。

## 5. 自动压缩与上下文组装（REQ-CMP）

- **REQ-CMP-01** Chat 和 Work 均自动压缩；普通用户不需要手动“新建对话以清空上下文”。
- **REQ-CMP-02** 处于软阈值时，在合适的安全边界安排压缩；达到硬阈值或已超出输入预算时，下一次模型请求必须先压缩、卸载大型内容或采取安全降级，再重新预算。
- **REQ-CMP-03** 压缩必须作为**独立模型请求**执行，默认使用当前会话所配置的模型及 API 设置，不把“总结自己”作为普通 Agent 对话消息插入主历史。
- **REQ-CMP-04** 压缩结果采用**自适应状态摘要**：不强制固定 JSON 或字段表格，由专用提示词要求保留事实、关键约束、已达成决定、不确定性和后续继续工作的必要信息。
- **REQ-CMP-05** Chat 摘要重点保留：用户要求与偏好、讨论结论及其理由、仍有争议的问题、重要引用与时间线；Work 摘要重点保留：任务目标、当前进度、产物/文件路径、已完成与待办操作、工具错误、下一步及阻塞条件。
- **REQ-CMP-06** 新模型上下文由“当前有效摘要 + 有界近期原始消息 + 必需的系统/工具信息 + 当前输入”组成；更早的原始消息只从模型上下文移出，不得从持久历史删除。
- **REQ-CMP-07** 压缩摘要应记录覆盖的原始消息范围、生成时间、版本、来源摘要版本和引用位置，便于查找原文、重试与恢复。
- **REQ-CMP-08** 待压缩输入本身超预算时，必须分批压缩并逐步合并；压缩请求同样接受 Token 预算检查。
- **REQ-CMP-09** 只有压缩结果生成并通过基本检查后，才可原子切换为当前有效摘要；旧摘要、原始历史与未完成状态不能先行丢弃。
- **REQ-CMP-10** 摘要不得把推测当成事实；工具成功与否未知时必须保留“不确定”，不能在摘要中补写未发生的步骤。
- **REQ-CMP-11** 避免连续反复压缩同一区间；采用范围边界、版本控制和最小压缩收益约束，降低无意义的重压缩和摘要漂移。

## 6. 历史持久化与权限边界（REQ-HIS）

- **REQ-HIS-01** 应用数据层保存权威原始历史，至少包括稳定会话 ID、消息/事件 ID、时间、角色、正文、工具调用及 call ID、工具结果、状态、附件或外部文件引用、摘要版本关联。
- **REQ-HIS-02** 原始历史应以可恢复的增量事件或等价持久结构写入。压缩、撤回当前上下文、切换模式视图均不得覆盖或丢失历史记录。
- **REQ-HIS-03** Work 不直接访问或修改应用数据层的权威历史；当前 Work 会话工作区内只保存可自由处理的**历史副本**。
- **REQ-HIS-04** 副本单向导出，允许 Agent 按现有工作区权限读取、搜索、编辑或删除；对副本的修改绝不反向写入应用权威历史。
- **REQ-HIS-05** 副本应由应用按需或增量刷新，并记录导出版本、水位线及时间；检索结果必须能够识别索引/副本是否落后于权威历史。
- **REQ-HIS-06** 历史副本采用适合脚本读取的结构化格式，建议 JSONL；文本、角色、时间和稳定消息 ID 可直接检索，原始消息与工具事件保持关联。
- **REQ-HIS-07** 工作区副本不得成为新沙箱例外：副本、索引、CLI 必须位于现有允许访问的工作区范围，且不得要求模型越权读取应用内部私有目录。
- **REQ-HIS-08** 导出前应剔除应用内部密钥、认证令牌和不应进入 Agent 工作区的私有元数据；普通会话内容仍按既有隐私与网络工具授权机制处理，不可假设用户原文天然无敏感内容。
- **REQ-HIS-09** 副本被删除、修改、损坏或被搜索脚本覆盖时，不得损害权威历史。应支持重新导出，且不能把副本的内容自动当作真实对话事实回写到权威层。

## 7. 混合历史检索与 Chat / Work 接入（REQ-SRH）

- **REQ-SRH-01** Chat 和 Work 共享一套检索排序规则与数据语义：精确关键词全文检索 + 本地 Embedding 语义检索 + 合并排序。默认可采用 SQLite FTS5、轻量本地 Embedding 与 RRF（倒数排名融合），不强制使用独立数据库服务。
- **REQ-SRH-02** Embedding 应支持离线本地运行；模型随应用部署或由安装器合规准备，首次使用路径明确。Embedding 失败、索引未就绪时必须回退到关键词检索。
- **REQ-SRH-03** 支持增量索引：依据稳定消息 ID、版本和内容指纹，仅重新处理新增或修改的可检索内容；索引是可删除、可重建的派生数据。
- **REQ-SRH-04** 检索必须限定于**当前对话**，除非将来另有明确的跨对话能力和授权；不得混入其他会话历史。
- **REQ-SRH-05** 查询应支持自然语言、可选时间范围、消息角色、结果条数、精确短语以及消息 ID 定位；返回消息 ID、时间、角色、相关片段与可供读取原文的定位信息。
- **REQ-SRH-06** 检索结果大小必须有默认限制与最大上限，禁止默认返回整段历史。原始长消息/工具结果可经 ID 按需读取，以控制再次造成的 Token 膨胀。
- **REQ-SRH-07** **Chat** 仅增加一个 `search_conversation_history` Tool Calling 工具，同一入口支持搜索与按消息 ID 获取上下文；该工具由应用内部安全访问权威历史及其索引。
- **REQ-SRH-08** **Work** 不增加新的模型可见工具；在当前工作区预置可直接调用的 Python CLI（建议 `work/.context/search_history.py` 或等价位置），使用现有命令执行工具查询当前工作区历史副本及索引。
- **REQ-SRH-09** Work 可自由编写其他脚本进一步处理副本；预置 CLI 只是一条高质量默认路径，不限制 Agent 的分析方式。CLI 应提供帮助信息、稳定的输出格式和清晰的索引状态提示。
- **REQ-SRH-10** 应在模式提示词中告知模型“哪些信息可能已被压缩、如何回查”，但不每轮自动把检索命中内容大段注入上下文；由模型按需触发回溯。

**推荐 CLI 使用体验（示意，不构成固定 API）：**

```bash
python work/.context/search_history.py "之前讨论的PPT设计要求" --top-k 8
python work/.context/search_history.py "自动压缩" --role user
python work/.context/search_history.py --message-id msg_123 --full
```

## 8. Work 大型工具结果与执行安全（REQ-WRK）

- **REQ-WRK-01** 大型终端输出、网页正文、日志和文档解析结果优先保存到允许的工作区文件，只将执行状态、关键片段、文件引用及必要元数据回传模型。
- **REQ-WRK-02** 工具输出文件化必须保留完整可恢复信息；不可以只保留模型自动摘要而丢掉原始结果。文件引用需与会话记录关联。
- **REQ-WRK-03** 完整工具调用链必须可追溯。并行调用中每个 `tool_call_id` 与结果对应关系不得因压缩丢失或错配；失败、取消、超时也应记录明确终态。
- **REQ-WRK-04** 不允许在尚未形成一致终态的工具调用批次中间任意删除或改写模型必需的关联上下文；应在安全边界进行压缩，必要时为继续执行保留最小完整调用片段。
- **REQ-WRK-05** Agent Loop 的运行状态、待执行任务、并行工具、用户中途发来的消息、暂停/取消请求及权限审批均由应用业务状态维护，不以模型摘要作为唯一真实来源。
- **REQ-WRK-06** 历史摘要中的“先前曾同意某操作”不是本次工具执行授权；原有低/中/高风险审批与工具级权限规则照常生效。
- **REQ-WRK-07** 工具输出即使来自历史文件或搜索结果，仍属于数据而非高优先级指令；不应凭历史中的文字绕过系统提示词与权限判断。

## 9. Chat 连续对话体验（REQ-CHT）

- **REQ-CHT-01** 用户无须区分“压缩前后”的会话，原对话标题、消息展示与可翻阅历史保持连续。
- **REQ-CHT-02** Chat 优先保留最近对话原文；用户询问较早信息时，模型可调用历史搜索工具，引用检索到的原始片段后再作答。
- **REQ-CHT-03** 搜索无结果、索引落后或只找到不完整内容时，助手不得把推测当成确定的历史事实；应说明未能确认的范围。
- **REQ-CHT-04** 对话搜索不应暴露其他会话或应用内部敏感存储；检索工具的返回内容仍纳入下一次请求 Token 预算。

## 10. 异常恢复与数据一致性（REQ-REC）

- **REQ-REC-01** 压缩请求因临时网络故障、限流或服务端错误失败时，在合理次数内重试；不覆盖旧摘要、不丢消息、不强制结束当前会话。
- **REQ-REC-02** 压缩输入过长时先分批处理；仍失败时尝试使用上一个已验证摘要、较少的近期原文和必要任务状态生成安全降级上下文。
- **REQ-REC-03** 单条输入、图片或单次工具结果本身超长时，应优先分片、提取、文件化或请求用户处理不可压缩内容；不能声称普通历史压缩一定能解决。
- **REQ-REC-04** 当连最小必要请求都无法发送，或模型服务不可用时，应用应保存完整进度并给出可恢复的错误状态，不能伪称任务仍在运行或自动完成。
- **REQ-REC-05** 压缩版本替换、历史副本导出与索引更新应具有一致性标识，防止并发消息、新工具结果或窗口关闭造成丢写和摘要覆盖。
- **REQ-REC-06** 应支持从最近一个验证通过的摘要版本及权威历史恢复。异常恢复后必须重新检查 Token 预算和 Tool Calling 关联完整性。
- **REQ-REC-07** 索引或 Embedding 失败不得影响基础聊天及 Work 执行：先回退关键词检索，再提供清楚的索引状态；背景重建不得阻塞全部功能。

## 11. 用户体验、设置与可观测性（REQ-UX）

- **REQ-UX-01** 自动压缩是后台维护行为，不额外生成普通可见的助手消息；在需要较长时间时可提供非侵入式状态提示。
- **REQ-UX-02** 用户可以查看原始聊天历史；压缩不改变用户已发送消息的显示内容，不把摘要伪装成用户原话。
- **REQ-UX-03** 应记录可诊断事件：模型能力、计数来源/估算精度、预算使用率、触发原因、压缩覆盖范围、压缩前后 Token、压缩耗时、错误类型、检索命中与索引水位线。
- **REQ-UX-04** 日志应默认避免记录密钥、完整隐私文本和过量工具正文；支持问题排查时不要求泄露整份原始历史。
- **REQ-UX-05** 阈值、输出预留、近期原文保留量、搜索结果上限及向量索引策略应以内部配置项实现；首版不要求提供复杂的用户设置界面。

## 12. 推荐初始参数与实施约束

| 项目 | 初始建议 | 说明 |
| --- | --- | --- |
| 压缩软阈值 | 输入预算 B 的 70% | 在安全边界计划压缩 |
| 压缩优先阈值 | 输入预算 B 的 80% | 下次请求前优先处理 |
| 压缩后目标 | B 的 50%–60% | 避免频繁重复压缩，无法达到时保留安全检查 |
| 摘要模型 | 当前会话模型 | 独立 API 请求，不插入主对话历史 |
| 摘要结构 | 自适应状态摘要 | Chat / Work 使用不同提示词，不强制固定字段 |
| 历史保留 | 权威原文全量保留 | 可配置数据保留策略另议，不因压缩删除 |
| Work 历史入口 | 工作区副本 + Python CLI | 无新模型工具，无新增沙箱目录例外 |
| Chat 历史入口 | 单个历史检索工具 | 关键词 + 语义混合检索 |
| Embedding | 本地轻量模型 | 可离线，索引可重建，失败回退全文搜索 |
| 检索注入 | 模型按需调用 | 不默认自动注入旧消息 |

**约束说明：** 以上百分比、具体路径、文件名及技术栈仅作为默认实现建议。任何替代实现只要达到本文行为与验收要求，均视为满足需求。

## 13. 交付物与验收标准

交付应至少包含：可运行的上下文管理逻辑、Chat 历史查询工具、Work 工作区历史副本与 CLI、索引初始化/增量更新/重建能力、压缩异常恢复、必要配置项和自动化测试。需提供面向开发者的简短说明，解释不同模型的计数可靠度、默认阈值、索引依赖和已知限制。

### 13.1 核心验收用例

| 编号 | 验收场景 | 预期结果 |
| --- | --- | --- |
| AC-01 | Chat 连续交谈并超过软阈值 | 在合适边界自动压缩，原会话持续可用，历史消息展示不变 |
| AC-02 | Work 高频并行工具调用并超过硬阈值 | 在安全边界压缩，所有 call ID 与结果仍正确关联，Agent 继续任务 |
| AC-03 | 模型工具 Schema / Skill 变大 | 发送前重新计算完整请求预算，不因只计算消息而超限 |
| AC-04 | 用户追问较早的原话或决定 | Chat 通过历史工具找到消息；Work 可用预置 CLI 找到工作区副本 |
| AC-05 | Work 修改或删除历史副本 | 权威历史不受影响，可重新导出和重建索引 |
| AC-06 | 关键词不同但语义接近 | 语义检索可贡献候选结果；精确术语也能被全文检索召回 |
| AC-07 | 本地 Embedding 不可用 | 退回关键词搜索，不影响继续对话或工作 |
| AC-08 | 一次工具输出远大于上下文 | 输出落盘并有可查引用，不直接塞满模型请求 |
| AC-09 | 压缩 API 超时或返回无效摘要 | 不覆盖上次有效摘要，按重试/降级策略恢复 |
| AC-10 | 压缩请求本身超出预算 | 分批压缩，而不是再次报上下文上限错误 |
| AC-11 | 模型在 Work 执行过程中收到新用户消息 | 消息与任务状态被可靠记录，压缩不丢失任何一方 |
| AC-12 | 工具调用被取消或失败 | 保留准确终态，摘要不能把失败写成成功 |
| AC-13 | 历史内容出现“绕过审批”字样 | 不改变真实审批规则，也不自动授予权限 |
| AC-14 | 模型切换为更小上下文窗口 | 用新能力值重新预算、必要时压缩或安全提示 |
| AC-15 | 应用重启 / 窗口关闭后恢复对话 | 权威历史、已验证摘要、任务状态与索引水位线可恢复 |
| AC-16 | 多模态输入的计数不可精确获得 | 明确采用估算和余量；不足时阻止危险超限请求 |

### 13.2 不得出现的回归

- 不得为了压缩删除或改写已保存的原始消息、工具结果和用户附件引用。
- 不得把 Work 的副本目录变成访问应用内部敏感目录的捷径。
- 不得因为检索/Embedding 模型损坏而强制删除会话或新建对话。
- 不得因为摘要中的叙述而跳过现有的工具风险审查、用户确认或沙箱规则。
- 不得向用户宣称“无上限上下文”；实际目标是可持续压缩与可恢复，而不是无限模型窗口。

## 14. 建议实施顺序

1. **基础正确性：** 权威历史事件、完整请求 Token 预算、请求前检查及诊断。
2. **可持续压缩：** 独立压缩请求、滚动状态摘要、近期原文、版本校验和异常恢复。
3. **Work 安全连续运行：** 大工具结果文件化、Tool Calling 安全边界和历史工作区副本。
4. **统一历史检索：** FTS5、Embedding、融合排序、增量索引与 CLI / Chat Tool 接入。
5. **端到端验收：** 长对话、长任务、并发工具、模型切换、数据损坏及错误恢复回归。

## 15. 需求结论

本次改造的核心不是“让模型记住无限文本”，而是让应用对有限模型窗口进行持续、可靠的管理：**按完整请求预算运行，用独立压缩保留可继续工作的状态，用完整原始历史保障可追溯，用混合检索按需恢复细节，并始终让工具执行状态和权限体系独立于模型摘要。**

最终用户体验应表现为：Chat 不因历史太长而被迫重开；Work 能在同一任务中长期工作；即使压缩或检索环节发生故障，系统仍尽可能恢复并清楚说明实际限制。
